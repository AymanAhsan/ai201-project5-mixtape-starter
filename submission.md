# Mixtape — Codebase Map

## Main files and what they do

**`app.py`** — Application factory. Creates the Flask app, configures the SQLite DB URI (overridable via `DATABASE_URL` env var), instantiates the shared `db = SQLAlchemy()` object, registers the four blueprints (`songs`, `playlists`, `users`, `feed`) under their URL prefixes, and calls `db.create_all()` on startup. There's no migration tool (no Alembic) — schema changes take effect by re-running `create_all`, which is why `seed_data.py` calls `db.drop_all()` first.

**`models.py`** — Defines 7 SQLAlchemy models plus 3 association tables:
- `User` — has a `listening_streak` int and `last_listened_at` timestamp maintained by `streak_service`, not stored anywhere else.
- `Song` — always has a `shared_by` (the user who shared it) and `share_note`; there's no separate "Share" model, sharing is just creating a `Song` row.
- `Tag`, `Rating`, `ListeningEvent`, `Playlist`, `Notification`.
- `friendships` — symmetric many-to-many self-join on `User` (both directions are inserted explicitly, e.g. in `seed_data.py`'s `add_friendship`).
- `song_tags` — plain many-to-many between `Song` and `Tag`.
- `playlist_entries` — many-to-many between `Playlist` and `Song` that also carries `position`, `added_by`, and `added_at` columns, so a song's place in a playlist is an explicit ordered field, not insertion order.

Every model has a `to_dict()` method — this is the only serialization layer; routes call `.to_dict()` (or a service returns pre-built dicts) and `jsonify()` the result directly. There are no separate schema/serializer classes.

**`routes/`** — One blueprint per resource area, each a thin layer that does request parsing, required-field validation, and HTTP status mapping (`ValueError` from a service → 400/404), then delegates to `services/`:
- `songs.py` — search, get one, rate, log a listen.
- `playlists.py` — create, get one, list songs in it, add a song to it.
- `users.py` — get profile, get streak, list/read notifications.
- `feed.py` — "friends listening now" and general activity feed.

No route touches `db.session` for business logic directly except `users.py`'s `get_user`, which does a direct `db.session.get(User, ...)` lookup since there's no dedicated user service for that.

**`services/`** — All business logic lives here, one module per feature area:
- `streak_service.py` — computes/updates `listening_streak` based on calendar-day deltas between `last_listened_at` and now.
- `feed_service.py` — builds the two friend-activity views from `ListeningEvent` rows.
- `search_service.py` — title/artist substring search over `Song`, joined to tags.
- `notification_service.py` — creates `Notification` rows and is also where `rate_song` and `add_to_playlist` live (rating and playlist-adding are treated as "things that might notify someone," so their logic sits next to notification creation rather than in a separate rating/playlist-membership service).
- `playlist_service.py` — playlist CRUD-ish reads and the ordered song query using `playlist_entries.position`.

**`seed_data.py`** — Wipes and repopulates the DB with 5 users/friendships, 25 songs (deliberately split into 0-tag / 1-tag / 3+-tag groups), 3 playlists, and a mix of recent/old `ListeningEvent`s. The tag-count grouping and recent-vs-old event split aren't incidental — they're structured so that specific known bugs (duplicate search results from tag joins, stale entries in "listening now") are directly observable against seeded data.

**`tests/`** — `test_streaks.py`, `test_search.py`, `test_playlists.py` exercise the corresponding services directly (not through HTTP), each importing `create_app`/`db` for an app-context fixture.

## Data flow — user rates a song

1. Client sends `POST /songs/<song_id>/rate` with `{user_id, score}` → `routes/songs.py:rate()`.
2. The route only validates presence of `user_id`/`score` (not the score range) and casts `score` to `int`, then calls `notification_service.rate_song(user_id, song_id, score)`.
3. `rate_song()` validates the 1–5 range, loads the `Song` and `User` (404-equivalent via `ValueError` if missing), and does an upsert: queries for an existing `Rating` by `(user_id, song_id)` (enforced unique by a `UniqueConstraint` on `Rating`) and updates its `score` in place, or inserts a new `Rating`.
4. **It never calls `create_notification()`.** Contrast with `add_to_playlist()` in the same file, which — after appending the song to the playlist — notifies `song.shared_by` (skipping self-notification) with a `song_added_to_playlist` notification. `rate_song` has no equivalent call to notify the sharer with a `song_rated`-type notification, so a user who shared a song gets no notification when a friend rates it, even though the seed data and route wiring look like they should support it.
5. The route returns `rating.to_dict()` with a 201 either way — so, from the API surface, rating "succeeds" whether or not anyone gets notified, which is why the gap isn't visible without tracing into the service.

## Other things worth knowing while reading the code

- `playlist_service.get_playlist_songs()` fetches songs ordered by `playlist_entries.position` but returns `songs[:-1]` — it silently drops the last song in the list on every call. Nothing downstream (route, tests) currently guards against this off-by-one.
- `search_service.search_songs()` does an `outerjoin` against `song_tags` without `.distinct()`, so a song with N tags produces N duplicate rows in the result — the "same song shows up twice" symptom scales with tag count, which is exactly why `seed_data.py` seeds a batch of songs with 3+ tags.
- `streak_service.update_listening_streak()` special-cases Sunday (`today.weekday() != 6`) when deciding whether to increment after a 1-day gap, so a listen on Sunday following a listen on Saturday does not increment the streak the way every other consecutive-day pair does.
- `feed_service.get_friends_listening_now()` filters `ListeningEvent.listened_at >= cutoff` where `cutoff = now - 24h`, then deduplicates to the most recent event per friend — so any friend who listened at all within the last 24 hours appears, not just people who are "currently" listening in a narrower sense.

## Patterns in how the app is organized

- **Routes never touch the ORM for business rules.** Every route's job is: parse request → call one service function → map `ValueError` to an HTTP error code → `jsonify`. All validation beyond "is this field present" and all `db.session` query/commit logic lives in `services/`.
- **Errors are communicated via `ValueError`, not custom exception types.** Every service raises a bare `ValueError` with a human-readable message for "not found" or "invalid input," and every route catches `ValueError` the same way and returns it as `{"error": str(e)}`. There's no distinction in the exception type between a 400 (bad input) and 404 (not found) — the route decides the status code, not the exception.
- **No serializer layer — `to_dict()` on the model is the API shape.** Whatever fields `to_dict()` includes are exactly what's exposed over HTTP; there's no separate DTO/view model.
- **Feature logic is grouped by "what it's about," not by CRUD verb**, and that grouping doesn't perfectly match file names: `rate_song` and `add_to_playlist` (which sound like they belong in a "ratings" or "playlists" service) actually live in `notification_service.py`, because the unifying theme of that file is "actions that can produce a notification," not "notification CRUD." Anyone editing playlist or rating behavior needs to know to look there too.
- **IDs are UUID strings everywhere** (`generate_uuid()` default on every model), not auto-incrementing integers, and association tables that need extra metadata (`playlist_entries`) are defined as raw `db.Table` objects rather than mapped classes, while simpler joins (`friendships`, `song_tags`) are also raw tables even though they carry no extra columns — the project doesn't use the SQLAlchemy association-object pattern anywhere.

## Root Cause Analysis

### Issue 1 — My listening streak keeps resetting (`streak_service.py`)

- **Reproduction steps:** Call `record_listening_event` for a user on a Saturday, then again on the following Sunday (one calendar day apart, the normal "consecutive day" case). Expected the streak to go 1 → 2 like any other consecutive-day pair; instead it reset to 1.
- **Navigation strategy:** Started at `routes/songs.py`'s `listen` endpoint, followed it into `streak_service.record_listening_event`, and from there into `update_listening_streak`. Ran the existing `test_streaks.py` suite first and noticed every consecutive-day case it covered used weekdays — there was no Saturday→Sunday case. Writing that case and watching it fail pointed straight at the day-of-week branch.
- **Root cause explanation:** The increment branch was `elif days_since_last == 1 and today.weekday() != 6:`. `weekday() == 6` is Sunday, so the *only* day this extra clause can make false is when `today` is a Sunday — meaning a listen exactly one calendar day after the last one fell through to the `else` (reset-to-1) branch specifically when that day happened to be a Sunday, even though the gap was identical to every other one-day gap that correctly increments.
- **Fix description:** Removed the `and today.weekday() != 6` clause so the branch is purely `days_since_last == 1`, matching the documented rule ("if the user listened yesterday: streak increments by 1") for every day of the week, not six-sevenths of them.
- **Side-effect check:** Reran `test_streak_starts_at_1_for_new_user`, `test_streak_increments_on_consecutive_day`, `test_streak_does_not_double_count_same_day`, and `test_streak_resets_after_skipped_day` — none of them depend on the weekday clause, so they still passed unchanged — then added `test_streak_increments_on_sunday` (Sat → Sun) to lock in the fix.

### Issue 2 — Friends Listening Now shows people from yesterday (`feed_service.py`)

- **Reproduction steps:** Seed a friend's `ListeningEvent` at 11pm "yesterday," then call `get_friends_listening_now` at, say, 1am "today." The friend showed up, even though the feature is meant to show who's listening *today*, not "within the last 24 hours."
- **Navigation strategy:** Traced from the feed route into `feed_service.get_friends_listening_now`, found `cutoff = datetime.now(timezone.utc) - RECENT_THRESHOLD` with `RECENT_THRESHOLD = timedelta(hours=24)`. Comparing it against `get_activity_feed` in the same file — which is explicitly documented as *not* recency-filtered — clarified that `get_friends_listening_now` was supposed to be the one with a real "today" boundary, and a rolling 24h window isn't that.
- **Root cause explanation:** A rolling `now - 24h` cutoff is a sliding window, not a calendar-day boundary — it accepts any event less than 24 hours old regardless of whether it happened "today" or late "yesterday." An event at 11pm yesterday is still within 24 hours of 10am today, so it passed the filter and was wrongly reported as "listening now."
- **Fix description:** Replaced the rolling window with a fixed midnight-UTC cutoff — `cutoff = datetime(now.year, now.month, now.day, tzinfo=timezone.utc)` — so the filter is "did this happen today (UTC)," a fixed boundary that resets at midnight instead of sliding forward every second.
- **Side-effect check:** Confirmed `get_activity_feed` (the deliberately-unfiltered adjacent function) was untouched and still returns older events unfiltered. Added `test_excludes_friend_who_listened_yesterday` (fails pre-fix, passes post-fix) alongside `test_includes_friend_who_listened_recently` and `test_excludes_friend_who_listened_over_24_hours_ago` to confirm both the new midnight boundary and the already-correct "far in the past" exclusion still hold.

### Issue 3 — The same song keeps showing up twice in search (`search_service.py`)

- **Reproduction steps:** Search for a song tagged with 3+ tags (e.g. `search_songs("Crown Heights")` against a song with `rap`, `hip-hop`, and `boom bap` tags). `seed_data.py` deliberately seeds a batch of 3+-tag songs specifically to make this bug observable.
- **Navigation strategy:** `seed_data.py`'s comment about grouping songs into 0-tag / 1-tag / 3+-tag batches pointed directly at `search_service.search_songs`. Reading the query showed `.outerjoin(song_tags, Song.id == song_tags.c.song_id)` with no `.distinct()`. I inspected the compiled SQL and the raw `song_tags` rows directly (`SELECT * FROM song_tags WHERE song_id = ...` returned 3 rows for the 3-tag song) to confirm the join really does fan out at the SQL level, one row per tag match, even before it reaches the ORM.
- **Root cause explanation:** An outer join from `Song` to `song_tags` produces one result row per matching tag row, not one per song. The query selects only `Song`'s own columns and never collapses those fanned-out rows, so a song with N tags contributes N (identical, from the caller's perspective) rows to the result — the duplication count scales exactly with tag count, which matches the bug report and explains why `seed_data.py` specifically seeds a 3+-tag group to surface it. Correct behavior requires collapsing on the song's identity after the join, which a plain `.all()` on a fanned-out join does not do on its own.
- **Fix description:** Added `.distinct()` to the query chain in `search_songs`, so duplicate `Song` rows produced by the tag fan-out collapse to one row per song regardless of how many tags it has.
- **Side-effect check:** Ran `test_search_no_duplicates_no_tag_song`, `_single_tag_song`, and `_multi_tag_song` together with `test_search_returns_matching_songs` and `test_search_returns_empty_for_no_match` — `.distinct()` only removes exact-duplicate rows, it doesn't change which songs match the title/artist filter, so a plain non-matching search still correctly returns `[]` and a genuine match is still found. *Note:* on the pinned SQLAlchemy 2.0.51 + SQLite combination in this repo, the legacy `Query` API happens to already fold duplicate full-entity rows by primary key before returning them to Python, so the symptom wasn't reproducible as a literal 3-item list in this exact environment — but the underlying SQL still fans out per tag (confirmed via the raw row count above), which is the actual condition the bug report describes. `.distinct()` makes the query correct independent of that implicit, ORM-version-specific behavior rather than relying on it.

### Issue 4 — No notification when a friend rates my song (`notification_service.py`)

- **Reproduction steps:** User A shares a song. User B calls `POST /songs/<id>/rate`. Check user A's notifications afterward (`get_notifications`) — expected a new notification, got none. Compare with user B adding the same song to a playlist instead, which does produce a `song_added_to_playlist` notification for user A.
- **Navigation strategy:** The issue text itself contrasts the two actions, so I opened `notification_service.py` and read `rate_song()` and `add_to_playlist()` side by side, since both live in the same file. `add_to_playlist()` ends with an explicit `create_notification(...)` call guarded by `song.shared_by != added_by_user_id`; `rate_song()` commits the `Rating` and returns with no equivalent call anywhere in the function. Grepping the file for `create_notification` confirmed it's called exactly once, from `add_to_playlist`, not from `rate_song`.
- **Root cause explanation:** `rate_song()` performs the upsert of a `Rating` row and commits, but never calls `create_notification` for the song's `shared_by` user. The notification-triggering step that exists for the structurally identical "someone did something to my shared song" case in `add_to_playlist()` was simply never written for the rating path — the gap isn't a wrong condition, it's a missing call, which is why it's invisible from the route (which returns 201 either way) and only visible by tracing into the service body.
- **Fix description:** Added a `create_notification` call at the end of `rate_song()`, after the commit, mirroring `add_to_playlist`'s `song.shared_by != user_id` self-notification guard, using a new `song_rated` notification type with a message including the rater's username and score.
- **Side-effect check:** Wrote `tests/test_notifications.py` with three cases: a friend rating notifies the sharer, a user rating their own song does *not* self-notify, and re-rating (the upsert/update path) still notifies. Before writing the fix into the tree, I stashed just the `notification_service.py` change and reran the suite — the "friend rates" and "re-rate" tests failed (0 notifications instead of 1 and 2) while the self-rating test passed regardless, confirming the self-notification guard logic itself was never broken — only the missing call was. I also manually exercised `add_to_playlist` and `rate_song` back to back on the same song and confirmed both notification types (`song_added_to_playlist` and `song_rated`) appear independently without interfering with each other.

### Issue 5 — The last song in a playlist never shows up (`playlist_service.py`)

- **Reproduction steps:** Create a playlist and add 5 songs at positions 1–5, then call `get_playlist_songs`. Expected all 5 songs back in position order; got only the first 4 — the song at position 5 was missing every time, regardless of playlist size.
- **Navigation strategy:** Followed `GET /playlists/<id>/songs` into `playlist_service.get_playlist_songs`. The query itself — join on `playlist_entries`, filter by `playlist_id`, `order_by(asc(playlist_entries.c.position))` — was correct and fully ordered. The bug was one line below: `return [song.to_dict() for song in songs[:-1]]`. Since the query was already provably correct (it returns all 5 rows in order), the missing song had to be in the post-query slicing, not the SQL.
- **Root cause explanation:** `songs[:-1]` drops the last element of whatever list the query returns, unconditionally, on every call — it's a hardcoded off-by-one that has nothing to do with playlist size or position values. Correct behavior requires returning the full list the query already produces; the slice was silently overriding an otherwise-correct query result, which is why the function's own docstring ("returns all songs in the playlist") didn't match its actual behavior.
- **Fix description:** Removed the `[:-1]` slice so the function returns `songs` in full.
- **Side-effect check:** Ran `test_playlist_returns_songs_in_order` to confirm the position-based ordering itself was never affected (only the count was wrong), and `test_empty_playlist_returns_empty_list` to confirm the empty-list edge case (`[][:-1]` is also `[]`, so this case had been silently correct-by-coincidence) still passes now that the slice is gone.
